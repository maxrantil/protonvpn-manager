# PRD: Keep the VPN's DNS in force while connected

**Document Version**: 0.2 (draft, revised after agent review)
**Date**: 2026-11-17
**Author**: Doctor Hubert (with Claude Code assistance)
**Status**: Approved 2026-11-17 (FR6 on by default, opt-out); S1 spike done (NM part), Tailscale part pending
**Related Issue**: #295 (related: #294)

---

## 1. Executive Summary

### Problem Statement

While the VPN is connected, NetworkManager can overwrite `/etc/resolv.conf` with the
LAN router's DNS (`172.20.10.1` and `fe80::…%wlan0`). Both addresses are on-link
(wlan0), so the tunnel's routes don't cover them:

- **Kill switch off (default)**: every DNS query leaves outside the tunnel over IPv4,
  and also over IPv6, because the IPv6 guard accepts `fe80::/10`. This is a **DNS leak**
  that reveals every visited hostname to the local network.
- **Kill switch on**: router DNS is blocked, so name resolution fails and the VPN looks
  broken, with no automatic repair.

`vpn status` still reports CONNECTED.

### Proposed Solution

Three layers:

1. **Prevent**: NetworkManager hands its DNS to openresolv, where the VPN's exclusive
   entry wins (removes the main cause).
2. **Repair**: the dispatcher hook puts the VPN's DNS back when NetworkManager reports a
   DNS change, for setups without layer 1 or where something else rewrites resolv.conf.
3. **Guarantee** (decision needed, FR6): while connected, DNS (port 53) may only leave
   through the tunnel, loopback or Tailscale, even with the kill switch off. This is the
   only layer that closes the leak window completely.

### Success Criteria

- With the VPN connected, no DNS query leaves through wlan0/eth* over IPv4 or IPv6,
  including during NetworkManager DNS updates, wifi reconnects and resume. This is
  measured with a packet counter or tcpdump on port 53, not inferred from resolv.conf.
- `/etc/resolv.conf` lists only the VPN's nameservers while connected.
- After `vpn disconnect`, after `vpn cleanup` and after an OpenVPN crash or SIGKILL,
  DNS works again (the network's DNS, or Tailscale's when it manages DNS).
- `vpn status` warns when connected but resolv.conf doesn't match the VPN's entry.
- No regression in Tailscale DNS pause/restore (direct and resolvconf modes).

## 2. Background & Context

### Current State

- `vpn-dns-update` (OpenVPN up/down helper, root) registers the pushed DNS with
  `resolvconf -x -a tun0.protonvpn` and forces `resolvconf -u` when resolv.conf was
  written by someone else. It runs **once** per tunnel up.
- NetworkManager 1.58.1 uses the default `rc-manager=symlink`. `/etc/resolv.conf` is a
  **regular file**, so NetworkManager writes it directly on every DNS update.
- The dispatcher hook `50-vpn-reconnect` reacts only to `up`/`connectivity-change` on
  wl*/eth*/enp*, and only with `AUTO_RECONNECT=true` and the kill switch on.
  It resolves the real user before anything else.
- The IPv6 guard (`VPN_IPV6_GUARD`, always on while connected) accepts `fe80::/10` and
  `ff00::/8`, including port 53.

### Problem Discovery (2026-11-17)

This came up in the post-reboot sanity check. About 1 s after `vpn connect`, NetworkManager
rewrote resolv.conf while openresolv still held `tun0.protonvpn → 10.96.0.1`. The
evidence is in #295. #294's resume probe shows the same fallback after resume.

## 3. Requirements

### Prerequisite: spike (before the PDR)

**S1**: On this machine, controlled, with auto-teardown:

- Set `rc-manager=resolvconf` and record what NetworkManager 1.58 runs: entry name,
  `-a` / `-d` / `-u`.
- Confirm that the VPN's `-x` entry suppresses NetworkManager's entries and Tailscale's.
- Confirm that the hook receives `dns-change`, and with what interface argument.
- Confirm whether tailscaled switches from "direct" to "resolvconf" mode, and whether
  `/etc/resolv.pre-tailscale-backup.conf` is left behind.

Layer 1 is built only if S1 confirms it works.

**S1 results (2026-11-17, NM 1.58.1, openresolv 3.17.4, VPN connected, auto-teardown)**:

- **Symlink mode (today)**: `nmcli general reload dns-full` reproduces the leak every time.
  resolv.conf becomes `# Generated by NetworkManager` with `172.20.10.1` and `fe80::…%wlan0`,
  while openresolv still holds `tun0.protonvpn`. `resolvconf -u` repairs it.
- **`dns-change`** reaches dispatcher hooks with an **empty interface** argument. It fired on
  each reload.
- **`nmcli general reload dns-rc` does not apply a new `rc-manager`**: NM kept writing the file
  itself. `nmcli general reload conf` does, with no wifi drop.
- **resolvconf mode**: NM registers an openresolv entry named **`NetworkManager`** (router
  IPv4 + IPv6). The VPN's `-x` entry wins: resolv.conf kept only `10.96.0.1` through
  `reload dns-full`.
- **Back to symlink mode**: NM leaves its `NetworkManager` entry in openresolv. Uninstall
  must run `resolvconf -f -d NetworkManager` (FR2).
- **Not yet tested**: Tailscale's mode flip (CorpDNS was paused at the time), wifi off/on,
  DHCP renew.

### Functional

- **FR1**: While this tool's VPN is up, resolv.conf is built from openresolv only, with the
  VPN's entry exclusive.
- **FR2** (layer 1): the installer adds `/etc/NetworkManager/conf.d/protonvpn-manager-dns.conf`
  with `[main] rc-manager=resolvconf`:
  - It does so only when NetworkManager runs, openresolv is the installed `resolvconf`
    (`resolvconf --version` names openresolv, and `-x` is supported), and
    systemd-resolved isn't running.
  - It applies the change with `nmcli general reload conf` (S1: `dns-rc` does not re-read rc-manager), never by restarting
    NetworkManager.
  - It says what it changed and how to opt out (`--no-nm-dns`).
  - Install while the VPN is connected must keep the VPN's DNS.
  - Uninstall removes the drop-in, runs `nmcli general reload conf`, then `resolvconf -f -d NetworkManager` (S1: NM leaves the entry behind).
- **FR3** (layer 2): the dispatcher hook handles `dns-change` in a separate branch:
  - It runs **before** user detection, config loading and the existing
    `validate_inputs`. It needs no user, no `AUTO_RECONNECT` and no kill switch.
  - It acts only when `vpn_is_healthy` is true and `resolvconf -l tun0.protonvpn` is non-empty.
  - It runs `resolvconf -u` unconditionally (idempotent), with no content comparison
    and no TOCTOU check.
  - It uses a fixed resolv.conf path (ignores `VPN_RESOLV_CONF` as root) and refuses to
    act when `/etc/resolv.conf` is a symlink.
  - It serialises runs with flock in `/run/protonvpn-manager` (root-owned, not a symlink)
    and is rate-limited (e.g. at most 3 runs per 10 s) to break a `dns-change` loop.
  - A failing `resolvconf -u` is logged and must not abort the hook under `set -e`.
- **FR4**: `vpn status` and `vpn-doctor` warn when connected and resolv.conf's
  nameservers don't match `resolvconf -l tun0.protonvpn` (not a hard-coded IP), and
  print the fix.
- **FR5**: Stale VPN DNS after a crash: when no VPN runs, `vpn cleanup`,
  `clear_stale_vpn_state` and `~/vpn-recover.sh` remove a leftover `tun0.protonvpn` entry
  and run `resolvconf -u` (most of this exists; verify and test the kill -9 path).
- **FR6** (layer 3, approved: on by default): while connected, a DNS guard
  (`VPN_DNS_GUARD`, IPv4 + IPv6, built like `VPN_IPV6_GUARD`, on by default, opt-out with
  `BLOCK_DNS_LEAKS=false`):
  - OUTPUT rules for udp and tcp dport 53, one rule per protocol (no multiport, #291):
    ACCEPT `-o tun+`, `-o lo` and `-o tailscale0`; REJECT everything else.
  - The REJECT is evaluated before the IPv6 guard's `fe80::/10` ACCEPT, so link-local
    router DNS is blocked too.
  - It's removed by `release_vpn_network_state` (disconnect, cleanup, stale state) and by
    `~/vpn-recover.sh`. After a crash it fails closed: no DNS, no leak, and `vpn cleanup` fixes it.
  - It doesn't cover DoT (853) or DoH, which are application choices and out of scope.
- **FR7**: Without the VPN, DNS behaves exactly as before.

### Non-functional

- **Security**: no new root code path parses user-controlled input. The FR3 branch reads
  nothing from the user's home.
- **Portability**: Artix/Arch with runit/OpenRC. With systemd-resolved, no NetworkManager
  or a non-openresolv `resolvconf`, FR2 is skipped (with a message). FR3, FR4 and FR6 still apply.
- **Reversibility**: one NetworkManager drop-in plus runtime firewall chains, all removed by
  uninstall, `vpn cleanup` or `~/vpn-recover.sh`.
- **Tests stay off the live VPN** (project rule): unit and integration tests use fakes
  (`VPN_RESOLV_CONF`, fake `resolvconf`/`ip6tables`), never the real firewall or resolv.conf.

### Out of Scope

- #294 (server host route after resume). Separate PRD, same hook.
- DNS over TLS/HTTPS chosen by applications.
- IPv6 traffic other than DNS (already handled by the IPv6 guard).

## 4. Options Considered and Leak Windows

| Option | Leak window left (kill switch off) | System change |
|---|---|---|
| A. NM drop-in `rc-manager=resolvconf` | tun0 up → `vpn-dns-update`; writers other than NM; resolvers without `-x` | One conf file |
| B. Hook re-runs `resolvconf -u` on `dns-change` | NM write → hook run (async, unordered); writers that don't trigger `dns-change` | None |
| C. Re-check on a timer | Up to the poll interval | None |
| D. NM `dns=none` | Like A, but breaks DNS without the VPN | One conf file |
| E. Port-53 guard while connected (FR6) | None for plain DNS; resolv.conf may still be wrong (FR4 shows it) | Runtime firewall chain |

**Recommendation: A + B + E, plus FR4 and FR5.** A and B keep resolv.conf correct, E makes
a wrong resolv.conf fail closed instead of leaking, and FR4 makes it visible.

**Tradeoff of E**: with the kill switch off, the user expects "nothing is blocked". E blocks
only DNS that would leak while the VPN is up, so name resolution through the LAN router stops
(e.g. local `*.lan` names). That is why it's opt-out and needs a decision.

## 5. Risks & Open Questions

1. **Tailscale mode flip** (S1): after A, tailscaled may switch to resolvconf mode. The
   connector records the mode at pause time, so a flip between connects is fine. Validate:
   restart tailscaled, pause/restore, MagicDNS names, and that no stale
   `/etc/resolv.pre-tailscale-backup.conf` is left behind.
2. **Install/uninstall while connected**: the reload triggers a rewrite. Test both.
3. **Loops**: `resolvconf -u` should not trigger NetworkManager's `dns-change`. The rate
   limit covers it anyway.
4. **Stale entries**: NetworkManager's openresolv entries after uninstall (removed by FR2's uninstall).
5. **Local names**: with E on, LAN-only names stop resolving while connected (documented, opt-out).
